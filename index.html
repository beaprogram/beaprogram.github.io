Implementation details for DecisionRail

How idempotency works

Every payment command requires an idempotency key scoped to the merchant. The key and a hash of the request are claimed in PostgreSQL in the same transaction that writes the payment, its ledger entries and its outbox row. Repeating a request returns the stored response. Reusing a key with a different payload returns 409 Conflict.

Why a modular monolith

The project’s design record keeps payment state, ledger, idempotency records and the outbox inside one database transaction. Separate services would have required cross-service consistency before the core payment rules were tested, and no measured scale requirement called for them. Read ADR 0001

What the failure tests check

Integration tests run in CI against a dedicated PostgreSQL and Kafka stack. They check that concurrent authorizations cannot overspend an account, that simultaneous retries produce one payment, one hold and one event, that a capture and void race ends in exactly one outcome, and that a failed outbox insert rolls back the payment and its idempotency claim. Delivery tests cover a Kafka outage and a crash after Kafka acknowledged a send. Browse the tests

Limitations

Delivery is at-least-once, not exactly-once, so consumers deduplicate by event ID. The local Kafka broker is a single node. A terminally failed event blocks later events for its own payment until an operator redrives it. Published outbox rows are not yet cleaned up. All funds are synthetic, and the project is not publicly deployed. Read the full list

Implementation details for Homebase

How it fits together

A React client calls a Java 21 Spring Boot backend. A separate Python FastAPI service handles natural-language retrieval, and PostgreSQL with pgvector stores the data. Docker runs the services together.

Access control and duplicate saves

JWT authentication identifies the user, and authorization checks in the service layer block access to other users’ data. A compound unique constraint on user and listing means the database itself rejects a second save of the same listing.

Testing

34 automated tests run in GitHub Actions CI: 20 JUnit tests for the Spring Boot backend, 4 pytest tests for the retrieval service, 6 pytest tests for data ingestion and 4 Vitest tests for the React client. The 25 Playwright end-to-end scenarios are a separate suite that runs against the full local stack.

Limitations

The Playwright suite needs the full stack running, so CI does not run it yet. There is no public demo with working backend services at the moment.
